## 4. 正式SQLite存储规划（不创建、不启用）

建议用代码仓库之外、受访问控制的本地专用数据根；远程文档只使用符号路径：

- 数据：<private-data-root>/v1/<bot-internal-id>/<persona-internal-id>/memory.sqlite3。
- SQLite的-wal/-shm与主库同目录；根目录仅运行账户及授权管理员访问，考虑卷级加密。
- bot/persona目录使用受控内部ID，禁止任意输入拼路径；仍保留数据库内租户外键和ACL，不靠目录隔离替代授权。
- 测试、开发、生产数据根严格分离。生产路径必须显式配置，不能默认为源码目录、OS临时目录或旧social状态文件；P1.1合成库接口继续不接受生产路径。
- 数据根、备份、日志不进入Git、普通自动同步或公共共享目录。WAL使用同机本地文件系统，不将活动库放在网络共享盘；具体机器路径只保留本地交付。

以上为设计建议，不代表已建立目录、设置ACL或实施生产存储。[SQLite WAL约束](https://sqlite.org/wal.html)。

## 5. 备份、恢复和迁移建议（不执行）

备份优先使用受支持的SQLite在线备份API生成一致性快照，也可评估VACUUM INTO；不在运行中只复制主.db而忽略WAL。备份加密并限制读取，定义RPO/RTO、保留期和独立故障域副本；同盘备份仅能帮助操作回滚，不能代替灾难恢复。[SQLite Backup API](https://sqlite.org/backup.html)、[VACUUM INTO](https://sqlite.org/lang_vacuum.html)。

每次备份/恢复校验SQLite/FK、FTS、迁移与repair账本，以及依赖可用性报告。恢复在隔离路径先演练；恢复旧备份前必须重放备份之后的撤销/tombstone屏障，否则可能让已删除数据复活。备份包含保留正文时，删除回执不得称物理完成，须有备份保留/销毁策略。

生产迁移建议：单一迁移协调者暂停写入→一致性备份→临时副本预演→事务迁移与FTS校验→账本及依赖验证→切换/恢复写入。失败保持禁用并回滚；已提交升级后的回退使用已验证备份及对应程序版本，不强制降版本/改checksum。schema_migrations和schema_repairs都必须核对，不能只看user_version。选定运行时后再次核对其SQLite版本和官方已知WAL问题；本次离线SQLite为3.51.3，不承诺未来部署运行时相同。
